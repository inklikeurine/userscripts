# AGENTS.md

Instructions for AI coding agents working on this repository. People: the
same rules apply to you.

## Read this first

This is a collection of browser userscripts, generated by AI under human
direction. People install them at their own risk.

**Firefox and Violentmonkey only.** Every script is written for Firefox with
[Violentmonkey](https://violentmonkey.github.io/) as the userscript manager.
Chrome, other browsers, Tampermonkey and Greasemonkey are not tested and not
supported: don't write code for them.

The maintainer does not read code. A change is judged by **trying it**: the
maintainer installs the script in Firefox with Violentmonkey and follows the
steps you write in the pull request. So your job is a change that works,
explained so that someone who won't read the code can try it.

## What's where

```text
userscripts/
├── AGENTS.md  CLAUDE.md  README.md  UNLICENSE  .gitignore  .claude/  .github/
├── <website>/
│   └── <script-name>/
│       ├── README.md
│       └── <script-name>.user.js
└── <another-website>/
    └── <script-name>/ …
```

- **A folder per website, then a folder per script.** No scripts at the
  root, none directly inside a website folder, and no shared libraries.
- **Website folder**: the site's name, lowercase, without `www.` or the
  ending: `youtube`, `github`, `sonarr`. Scripts that work on any site go in
  `any-site/`.
- **Script folder**: lowercase words joined by hyphens, saying what the
  script does: `hide-sidebar`, `quick-tags`. Don't repeat the site's name.
- The `.user.js` file has the same name as its folder.
- Every script stands on its own: it never uses files from another script
  folder.

## Web addresses

The repository is `https://github.com/inklikeurine/userscripts`. Every web
address in a script or README comes from it; never invent another host or
path.

| Purpose | Value |
|---|---|
| `@namespace` (the same in every script) | `https://github.com/inklikeurine/userscripts` |
| `@homepageURL` | `https://github.com/inklikeurine/userscripts/tree/main/<website>/<script-name>` |
| `@supportURL` | `https://github.com/inklikeurine/userscripts/issues` |
| `@downloadURL` and `@updateURL` (the same) | `https://raw.githubusercontent.com/inklikeurine/userscripts/main/<website>/<script-name>/<script-name>.user.js` |
| The script README's "Install" link | the same address as `@downloadURL` |

Violentmonkey recognises an installed script by `@namespace` plus `@name`,
so the namespace never changes. It looks for updates only through
`@downloadURL` and `@updateURL`; without them, no update ever reaches anyone.

## The root README

`README.md` at the root holds, in this order:

1. That these are AI-generated userscripts, provided as they are: **use at
   your own risk**.
2. That they are **tested in Firefox only**, with **Violentmonkey** as the
   only supported userscript manager.
3. A **Userscripts** section listing every script, under a heading per
   website, each linking to its folder with a one-line description. Adding,
   renaming or removing a script updates this list in the same pull request.
4. A short **License** section pointing to `UNLICENSE`.

## Each script

### Its `README.md`

Every script folder has a README, with:

1. **Title**: the script's name.
2. **What it does**: one or two plain paragraphs.
3. **Where it runs**: the sites or address patterns it matches.
4. **Install**: a link to the raw `.user.js` (the `@downloadURL`), and a
   line saying Violentmonkey for Firefox is needed.
5. **Notes / caveats**: the `GM_*` permissions it uses, any web requests it
   makes, and what may break when the site changes.
6. A **Firefox only** notice: written for Firefox, not tested in any other
   browser.
7. An **AI-generated** notice: generated by an AI agent, used at the user's
   own risk.

### Its `.user.js`

- It starts with a userscript metadata block (`// ==UserScript==` …
  `// ==/UserScript==`) with: `@name`, `@namespace`, `@version`,
  `@description`, one or more `@match`, `@grant`, `@run-at`,
  `@homepageURL`, `@supportURL`, `@downloadURL`, `@updateURL`. The address
  keys take exactly the values above.
- `@grant none` unless the script really needs a `GM_*` function; then list
  only the ones it uses, use their plain `GM_*` form, and name them in the
  README. Prefer plain page code and `localStorage` over `GM_*` storage.
- Plain JavaScript, no build step. No outside libraries unless there is no
  reasonable alternative; then load it with `@require` and explain it in the
  README.
- Nothing that only works in Chrome-based browsers.
- Readable by someone who didn't write it: short functions, and comments
  where the site's page structure is not obvious.

### Writing the script

AI-written userscripts fail in the same five ways:

- **Pages that don't reload.** YouTube, GitHub, Reddit and most large sites
  change page without reloading. A script that runs once works on the first
  page and never again. Watch for changes (a `MutationObserver` on
  `document.body`, not run on every tiny change) or listen for the site's
  own navigation event, and apply again.
- **Running twice.** Applying again must not add things twice. Mark what you
  added (a `data-<script-name>` attribute or an `id`) and check for it first.
- **When it runs (`@run-at`).** At `document-start` the page doesn't exist
  yet; at `document-idle` it's too late to stop a flash of what you're
  hiding. Style-only scripts: `document-start` and a `<style>` element.
  Scripts that change the page: `document-idle` plus watching for changes.
- **Finding elements.** Sites use scrambled class names. Prefer `id`,
  `aria-*`, `data-*`, custom element names and the page's structure over
  names like `.css-1a2b3c`.
- **The page's own code.** With `@grant none` the script shares the page's
  `window`. With any `GM_*` grant it runs walled off, and the page's
  `window` is `unsafeWindow`. Don't reach into a site's code when there is a
  way through the page itself.

## Checking your work

There are no automated checks on pull requests here yet, so check these
before you open one:

- **Layout**: folder and file names follow the rules above; the script has
  its README with all seven parts; the root README lists it.
- **Metadata**: every required key, the address values from the table,
  legal `@match` patterns and `@run-at` value, and `@grant` listing exactly
  the `GM_*` functions the code calls (`none` if it calls none).
- **Syntax**: `node --check <script-name>.user.js` succeeds.
- **In Firefox**: install it in Violentmonkey and try it on the real site.

## Versions: leave them alone

**Don't change `@version`.** The maintainer raises it once, in a release
pull request, when a batch of changes is ready. That matters more here than
anywhere: Violentmonkey updates installed scripts from `main` as soon as
`@version` goes up, so **merging a version change into `main` is the
release**.

The maintainer uses two numbers, **Major.Minor**, with Minor always at least
two digits:

- **Major** goes up for new features or changed behaviour, and Minor goes
  back to `00`.
- **Minor** goes up for fixes that add or change nothing. Fixing a script a
  site broke is a fix, however big.

New scripts start at `1.00`: `1.00` → fix → `1.01` → new feature → `2.00`.
After `1.99` the next fix is `1.100`, not `2.00` (each number is compared on
its own, so `1.100` comes after `1.99`). Never three numbers (`1.0.0`) and
never a one-digit Minor (`1.0`).

A new script's first pull request adds it at `1.00`.

## Your pull request

Fill in the pull request template (`.github/pull_request_template.md`):

- **One fix or feature per pull request.**
- **Say which AI tool wrote it**, and roughly how much of it.
- **Report three checks by these exact names**, and tick only what was
  actually done:
  - **Validated**: the checks under "Checking your work" (layout, metadata,
    syntax) passed.
  - **Automated Test**: the script was run in an automated Firefox, on the
    real site or a saved copy of it, and its effect was checked with no
    errors. If not, say why.
  - **Manual Review**: leave unticked. It means a person tried the change in
    real Firefox with Violentmonkey, and the maintainer does that before
    merging.
- **Write "How to try it"** as numbered steps. Each step is something to do
  and what should happen, for example "Open a series page in Sonarr. A Tags
  button appears beside Edit." Always include installing the script from
  the pull request's branch and opening the browser console to see that it
  shows no errors from the script. "Check that it works" is not a step.
  Write the steps from your change, not the whole script.

**Never say a change was "tested in Firefox" or "works" unless a person
tried it in real Firefox with Violentmonkey.** Say exactly what you ran.

## Don't

- Don't add a `package.json`, bundler, linter config or build step. This is
  a flat collection of standalone files.
- Don't add any license but the Unlicense, or license and copyright lines at
  the top of files.
- Don't commit personal data: names, emails, addresses, saved copies of a
  signed-in page, or details of your own computer or network.
- Don't collect data, phone home, or make web requests beyond what the
  script is for. Anything that makes requests says so in its README.
- Don't change `@namespace`, a script's `@name` or its folder: Violentmonkey
  would treat it as a new script and existing installs would stop updating.
- Don't create or delete tags or releases, or delete branches other than
  your own.
